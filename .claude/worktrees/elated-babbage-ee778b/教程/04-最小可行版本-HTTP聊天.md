# 第 4 章：最小可行版本 —— 完整的 HTTP 聊天

> 上一章我们把前后端各自能跑起来了，但它们还是两座孤岛。这章我们把它们联通，做出一个真正能聊天的应用——虽然 AI 还是假的，但整个框架搭好之后，下一章换成真 AI 只需要改一个函数。

---

## 4.1 先想清楚要做什么

在动手之前，先在脑子里把这章要做的事过一遍。

用户打开页面，输入"你好"，点发送。这条消息要跑一个来回：从浏览器出发，到我们的 Python 后端，后端生成回复，再把回复送回浏览器显示出来。听起来简单，但里面藏着一个问题——

**HTTP 是没有记忆的。**

每次前端发请求，对后端来说都像是第一次见面。你发"你好"，我回"你好"。你再发"然后呢"，后端完全不知道你刚才说了什么，因为它已经把上一次的事忘干净了。

这就是为什么我们需要**会话（Session）**。

---

## 4.2 会话是怎么工作的

解决方法其实很朴素：给每个用户发一张"号码牌"，叫做 `session_id`。用户每次发消息都带上这个号码，后端看到号码，就知道去哪里找这个用户之前说过的话。

```
用户第一次发消息 → 后端：你是新来的，给你分配号码 "abc-123"
用户带着 "abc-123" 说 "你好" → 后端找到 "abc-123" 的历史，追加，生成回复
用户带着 "abc-123" 说 "然后呢" → 后端找到完整历史，知道上文，生成回复
```

号码牌存在哪里？前端拿到之后存在 JavaScript 的一个变量里，每次发请求都带上。后端这边用一个 Python 字典来存所有用户的历史，键是 `session_id`，值是这个用户的消息列表。

这个方案最大的缺点是：服务器一重启，字典就没了，历史全丢。后面的章节我们会改成存数据库，但现在先把流程跑通。

---

## 4.3 后端：接收消息、管理历史、生成回复

后端要做三件事：

**第一件**：定义请求和响应的数据格式。前端发过来的是 JSON，我们用 Pydantic 的 `BaseModel` 描述它长什么样。`session_id` 是可选的，第一次发消息时不传，后端自动生成一个。

**第二件**：实现会话逻辑。收到请求时，检查有没有带 `session_id`、有的话有没有对应的历史，没有就新建一个。把用户的消息追加进历史，生成回复，再把回复追加进历史。

**第三件**：生成回复。现在先用关键词匹配做一个假的——说了"你好"就返回欢迎语，问"记得"就告诉他聊了几轮。这个函数下一章直接换成调 LLM API，接口不变。

> **你可能会问**：为什么要把 `generate_reply` 单独写成一个函数，而不是直接写在路由里？
>
> 就是为了下一章换起来方便。函数边界就是替换边界，路由负责处理 HTTP，生成回复的事交给专门的函数，各管各的。

写完之后，在终端里启动：

```bash
uvicorn main:app --reload
```

`--reload` 的意思是代码修改后自动重启，开发阶段非常方便。

打开浏览器，访问 `http://127.0.0.1:8000/docs`——这是 FastAPI 自动生成的接口文档，在里面可以直接测试 `/api/chat` 接口，不用写任何前端代码就能验证后端是否正常工作。

> **试一下**：在 `/api/chat` 里填入 `{"message": "你好"}`，点 Execute，你应该看到后端返回了 `reply`、`session_id` 和 `history_length`。再用这个 `session_id` 发第二条消息，看看 `history_length` 有没有变成 2。

---

## 4.4 前端：发请求、展示回复、记住 session_id

前端需要做的事：用户点发送，把消息和当前的 `session_id` 一起打包成 JSON，用 `fetch` 发 POST 请求出去，等后端回应，把回复显示在界面上，同时把后端返回的 `session_id` 保存下来留给下次用。

有几个细节值得展开说：

**为什么要等后端回应才显示消息？** 现在我们先显示用户的消息，然后放一个"正在思考"的动画，等后端返回再把动画换成真正的回复。这个顺序让用户感觉响应及时，不会觉得自己的消息"消失"了。

**为什么要 `try/catch`？** 网络请求随时可能失败——服务器没开、网络断了、后端报错了。不处理这些情况，用户就只能看着页面卡死，完全不知道发生了什么。`catch` 里我们把错误显示成一条红色消息，至少让用户知道出了什么问题。

**`sendBtn.disabled = true` 是什么意思？** 在等后端回应的这段时间里，把发送按钮禁用，防止用户连续点击发出多个重复请求。`finally` 块里再把它恢复，不管请求成功还是失败都会执行。

> **`try/catch/finally` 的结构**：`try` 里放可能出错的代码，出错了跳到 `catch`，不管有没有出错，`finally` 里的代码都会执行。这个模式在处理网络请求时非常常用。

---

## 4.5 联调：让前后端说上话

后端跑起来了，前端也写好了，但如果你直接在浏览器里打开 `index.html`，发消息的时候十有八九会报一个 **CORS 错误**。

这是浏览器的安全机制在搞事情。前端文件是从本地磁盘加载的（地址是 `file://...`），而后端在 `localhost:8000`，这两个"来源"不一样，浏览器默认不允许这种跨来源的请求。

解决方法有两个：

**方法一（推荐）**：让后端直接提供前端文件。在 `main.py` 里挂载 `StaticFiles`，让 FastAPI 也能服务 HTML/CSS/JS 文件。这样前端和后端的来源就一样了，不存在跨域问题。启动后端，直接访问 `http://127.0.0.1:8000`。

**方法二**：在后端加 CORS 中间件，明确告诉浏览器"我允许来自任何地方的请求"。第 3 章已经写了这个，但本地文件的情况下不一定够用，所以方法一更稳。

> 这是新手非常容易踩的一个坑，你将来调接口的时候还会再遇到它。记住这个关键词：**CORS**，跨域资源共享，浏览器的安全机制，解决方法是在后端允许跨域，或者让前后端同源。

现在打开页面，试着发几条消息：

- 发"你好"，应该得到一条欢迎回复
- 发"你还记得我们聊了多少轮吗"，后端会告诉你轮数
- 注意页面顶部有个会话 ID 和轮数的显示，随着对话进行它会更新
- 刷新页面，会话 ID 变成 null，重新开始——这就是内存存储的局限

## 4.6 完整的数据流，再走一遍

把这一章做的事情连起来看：

```
用户输入"你好"，点发送
    ↓
前端：把消息 + session_id 打包成 JSON，fetch POST /api/chat
    ↓
后端：解析请求体，发现 session_id 是 null
    → 新建 session_id = "abc-123"，sessions["abc-123"] = []
    → 追加 {role: "user", content: "你好"}
    → generate_reply() 返回 "你好！我是 AI 助手..."
    → 追加 {role: "assistant", content: "..."}
    → 返回 {reply, session_id: "abc-123", history_length: 1}
    ↓
前端：拿到响应，sessionId = "abc-123" 存起来
    → 把 reply 显示成一条 assistant 消息
    ↓
用户再发"然后呢"
    ↓
前端：这次请求带上 session_id: "abc-123"
    ↓
后端：找到 sessions["abc-123"]，已经有一条 user 和一条 assistant 消息
    → 追加新的 user 消息，生成回复
    → history_length 变成 2
```

每一层都只做自己该做的事：前端负责展示和发请求，后端负责维护状态和生成回复，用 `session_id` 把它们串起来。

## 4.7 这章做完了，但问题也很明显

现在的版本有几个你一眼能看出来的问题：

回复是假的。`generate_reply` 就是几个 `if` 语句，下一章我们把它换成真正的 LLM API，只改这一个函数，其他的都不动。

用户要等后端完全回完才能看到回复。如果 AI 要想 5 秒钟，用户就得盯着转圈圈看 5 秒。第 7 章我们用 WebSocket 改成流式输出，边生成边显示。

刷新就丢历史。第 11 章改成数据库。

一张椅子不够坐——现在所有用户的历史都混在一个 Python 进程里，服务器重启就全没了，而且也没有账号区分。第 11 章一起解决。

这些问题现在都先放着，架子搭好是这章最重要的事。

---

## 本章小结

- HTTP 无状态，用 `session_id` 给请求"认脸"，用 Python 字典存历史
- Pydantic 的 `Optional[str] = None` 让字段可选，第一次不传，后端自动生成
- `uuid.uuid4()` 生成一个全球唯一的随机 ID，碰撞概率可以忽略不计
- CORS 是浏览器的安全机制，前后端同源或者后端显式允许都能解决
- `try/catch/finally` 处理请求失败，`disabled` 防止重复提交，这两个是处理异步操作的标准模式
